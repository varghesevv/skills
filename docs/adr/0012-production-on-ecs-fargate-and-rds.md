# ADR-0012: Production on ECS Fargate and Amazon RDS for PostgreSQL

- **Status:** Proposed
- **Date:** 2026-10-22
- **Deciders:** Project owner (open points are listed below and in `docs/open-questions.md`, Q18 to Q23)

## Context

The demo runs on one Lightsail instance with PostgreSQL in a container ([ADR-0008](0008-aws-lightsail-single-instance-demo-deployment.md)). That ADR says it is not suitable for production and that a new ADR decides the production architecture. The owner plans production within 1 to 2 months of the demo.

What production needs that the demo does not have:

- A database that survives the loss of a machine: automated backups, point-in-time recovery, encryption, optional Multi-AZ failover.
- No single machine to patch and no SSH to open on the internet.
- Secrets injected from a managed store (the application already reads secrets only from environment variables, [ADR-0011](0011-secrets-from-environment-only.md)).
- Deployments without downtime, and a way to roll back to the previous image.
- Real email for password reset (today the reset link is only written to the log).
- Rate limiting and a web application firewall at the edge, and alarms that page a person.
- Files (reports) that survive container restarts and are shared by the API and the worker.

Facts about the application that shape the choice: the API and the worker are stateless except for report files written to `REPORTS_OUTPUT_DIR` and read back by the API for downloads; the worker must run **exactly one** instance (otherwise scheduled reports run twice); the same container image is used in every environment and the database is reached only through `DATABASE_URL`.

## Decision

Build production with Terraform in `infra/terraform/envs/prod`, in the same region (`ap-south-1`), reusing the modules and the pipeline structure of the demo:

1. **Database:** Amazon RDS for PostgreSQL 16 in private subnets, encrypted with KMS, automated backups with 14 days of point-in-time recovery, deletion protection, Multi-AZ on (Q22 may turn it off to save cost). The security group admits only the application tasks. The master password is generated by RDS into AWS Secrets Manager.
2. **Application:** Amazon ECS on Fargate with three services from the images already built for the demo (promoted by tag, never rebuilt): `api` (2 tasks), `web` (2 tasks), `worker` (exactly 1 task, deployment settings `minimumHealthyPercent=0`, `maximumPercent=100`). Migrations run as a one-off task before the services are updated.
3. **Edge:** an Application Load Balancer with an ACM certificate, HTTP redirected to HTTPS, routing `/api/*` and `/health` to `api` and everything else to `web`, with AWS WAF rate-based rules (replaces Caddy and the demo proxy). Security headers (including the Content-Security-Policy used in the demo) are added by the `web` container's nginx so they do not depend on the proxy.
4. **Reports:** stored in an S3 bucket instead of a local folder. The report writer and the download endpoint get a small storage interface with a local-folder implementation (development, demo) and an S3 implementation (production). This is application work and is a prerequisite for the Fargate design, because tasks have no shared disk.
5. **Secrets and settings:** AWS Secrets Manager and SSM Parameter Store, injected into task definitions as environment variables (ADR-0011 still holds: no secrets in files, images or logs).
6. **Email:** Amazon SES (Q21) for password reset and later notifications. The reset-link-in-log behaviour stays only for `local` and `demo`.
7. **Deployment:** a `deploy-prod` GitHub Actions workflow behind the GitHub Environment `prod` (required reviewers), assuming an OIDC role limited to ECS, the ECR/GHCR pull, and the specific task definitions. The image tag that passed in demo is the one promoted. Rollback is deploying the previous tag.
8. **Observability:** CloudWatch Logs with 30 days of retention, alarms on 5xx rate, task count, RDS CPU, storage and connections, and the existing external uptime check, all sending to one email or chat topic (Q22 sets the targets).
9. **Accounts and access:** production uses its own Terraform state, IAM roles and GitHub Environment; Q20 decides whether it is also a separate AWS account. Nobody gets SSH because there is no server; operators use `aws ecs execute-command` (audited) for the rare console task such as creating an admin.

## Alternatives considered

- **Keep the Lightsail instance and move only PostgreSQL to RDS (or the Lightsail managed database).** Cheapest and closest to the demo, and a reasonable stepping stone. Rejected as the end state because the application server stays a single point of failure with manual patching and SSH, and zero-downtime deploys are not possible.
- **Lightsail containers service plus Lightsail managed database.** Simple console and predictable price, but containers have no persistent volumes (reports would need S3 anyway), limited scheduling control for the single worker, and less room to grow. Rejected for production; a good fit for a second demo.
- **EC2 with Docker Compose and RDS.** More control and cheaper than Fargate at small sizes, but we would keep owning OS patching, Docker upgrades and SSH access. Rejected for the operational load on a small team.
- **Kubernetes (EKS).** Far more machinery than three small services need.
- **AWS App Runner.** Simple, but weaker support for a singleton background worker and private networking to RDS; revisit if Fargate proves too heavy.

## Consequences

- Production is more expensive than the demo (Fargate tasks, ALB, NAT or VPC endpoints, RDS Multi-AZ, WAF). Rough cost to be confirmed with the AWS Pricing Calculator before approval; Q22 answers decide the sizes.
- Application work comes first: an S3 report storage implementation, production-grade email sending, and a check that nothing assumes a single API process (login throttling already uses the database, which is fine).
- The demo stays as it is and keeps fake data only; it may be destroyed when production exists.
- New Terraform modules are needed: network, rds, ecs_service, alb_waf, ecr or GHCR pull access, s3 reports, ses, monitoring. The `envs/prod` layout reuses `bootstrap` for the state bucket and the OIDC provider, with a separate prod role.
- A go-live checklist (backup restore test, load test, security review, privacy review per Q23, DNS cut-over, alarm test) gates the first production deploy.
- If the owner prefers a cheaper start, the Lightsail instance with RDS option can be built first and replaced later without changing the application, because only `DATABASE_URL` and the report storage setting differ.
